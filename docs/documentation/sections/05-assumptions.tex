\section{Założenia wstępne}

\subsection{Założenia projektowe}

\begin{itemize}
  \item \textbf{Aplikacja webowa projektowana od telefonu.} Interfejs powstaje najpierw dla małych ekranów (\emph{mobile-first}) i~jest rozszerzany na tablety i~komputery zgodnie z~zasadami RWD. Najczęstsze czynności, takie jak dodanie wydatku czy odhaczenie zakupu, są dostępne bez zbędnej nawigacji.
  \item \textbf{Gospodarstwo domowe jako podstawowa jednostka danych.} Wydatki, spłaty, listy zakupów i~obowiązki należą do gospodarstwa. Dostęp do nich mają wyłącznie bieżący członkowie, a~zakres uprawnień zależy od roli: dane finansowe i~ustawienia gospodarstwa są chronione, a~codzienne listy pozostają otwarte dla wszystkich członków.
  \item \textbf{Moduły włączane niezależnie.} Każde gospodarstwo samodzielnie decyduje, z~których modułów korzysta (wydatki, obowiązki, zakupy, sztuczna inteligencja). Wyłączenie modułu blokuje zmiany, ale nie usuwa danych.
  \item \textbf{Dokładne obliczenia finansowe.} Kwoty przechowywane są jako liczby całkowite w~jednostkach podrzędnych waluty, co eliminuje błędy zaokrągleń arytmetyki zmiennoprzecinkowej. Reszty z~podziału kwot rozdzielane są metodą największych reszt w~sposób deterministyczny, więc suma części zawsze równa się kwocie wydatku. Waluty nie są przeliczane, a~salda prowadzone są oddzielnie dla każdej z~nich.
  \item \textbf{Ewidencja zamiast realizacji płatności.} Aplikacja rejestruje przelewy wykonane poza nią. Spłata zgłoszona przez płacącego wymaga potwierdzenia przez odbiorcę, zanim zostanie uwzględniona w~saldach.
  \item \textbf{Sztuczna inteligencja jedynie proponuje.} Każdy wynik modelu (odczyt paragonu, kategoria, dopasowanie do listy zakupów) jest weryfikowany przez użytkownika przed zapisem, a~odpowiedź modelu jest dodatkowo sprawdzana pod kątem zgodności ze schematem danych.
  \item \textbf{Ochrona danych przy korzystaniu z~AI.} Moduł sztucznej inteligencji jest domyślnie wyłączony i~włącza go administrator gospodarstwa. Do dostawcy modelu trafiają wyłącznie dane niezbędne do realizacji zadania (obraz paragonu, opisy wydatków, nazwy kategorii i~pozycji listy zakupów), bez imion, adresów e-mail i~identyfikatorów użytkowników. Wymagane jest, aby dostawca nie przechowywał przesłanych danych ani nie wykorzystywał ich do trenowania modeli. Liczba zapytań do modelu jest ograniczona dziennym limitem na gospodarstwo.
  \item \textbf{Wspólne kontrakty API.} Schematy żądań i~odpowiedzi są zdefiniowane raz, we wspólnym pakiecie, i~wykorzystywane zarówno przez interfejs użytkownika, jak i~przez serwer.
\end{itemize}

\subsection{Organizacja pracy i~harmonogram}

Projekt realizuje czteroosobowy zespół w~ciągu dziesięciu tygodni. Zadania są prowadzone jako zgłoszenia (\emph{issues}) w~serwisie GitHub i~grupowane w~epiki odpowiadające obszarom funkcjonalnym, oddzielnie dla serwera i~interfejsu użytkownika. Każda zmiana trafia do głównej gałęzi przez \emph{pull request}, w~którym proces CI sprawdza styl kodu, typy, budowanie oraz testy jednostkowe, integracyjne i~E2E. Po scaleniu zmian do głównej gałęzi następuje automatyczne wdrożenie: najpierw migracje bazy danych, następnie serwer, a~na końcu aplikacja webowa.
