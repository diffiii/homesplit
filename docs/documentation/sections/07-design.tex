\section{Projekt produktu programowego}

\subsection{Architektura systemu}

HomeSplit ma architekturę klient-serwer z~trzema warstwami: aplikacją webową działającą w~przeglądarce, serwerem aplikacji udostępniającym API oraz warstwą danych. Kod wszystkich części znajduje się w~jednym monorepozytorium, podzielonym na trzy pakiety:

\begin{itemize}
  \item \texttt{web} - aplikacja webowa w~Next.js i~React,
  \item \texttt{backend} - serwer aplikacji w~NestJS,
  \item \texttt{contracts} - wspólne kontrakty API: schematy Zod, typy, mapa endpointów oraz logika podziału kwot.
\end{itemize}

Komponenty systemu i~przepływ danych między nimi przedstawiono na rys.~\ref{fig:architektura}.

Przeglądarka komunikuje się wyłącznie z~serwerem Next.js. Ten serwer przekierowuje żądania kierowane pod ścieżkę \texttt{/api/*} do serwera API, dzięki czemu aplikacja i~API mają wspólne pochodzenie (\emph{origin}), a~ciasteczka sesji są traktowane przez przeglądarkę jako własne. Serwer API odpowiada za całą logikę biznesową i~jako jedyny ma dostęp do bazy danych, magazynu plików, usługi poczty i~dostawcy modeli AI. Wyjątkiem jest pobieranie załączników: przeglądarka pobiera je bezpośrednio z~magazynu obiektów, korzystając z~krótko ważnych, podpisanych adresów URL wystawianych przez serwer API.

Aplikacja webowa i~serwer API są wdrażane jako osobne usługi na platformie Render. Lokalnie baza danych i~magazyn plików działają w~kontenerach Docker Compose.

\subsection{Decyzje architektoniczne}

\begin{description}
  \item[Wspólne kontrakty API.] Każdy endpoint jest opisany raz, w~pakiecie \texttt{contracts}, wraz ze schematami żądania i~odpowiedzi. Serwer waliduje na ich podstawie dane wejściowe, aplikacja webowa generuje z~nich typowane funkcje dostępu do API, a~atrapy API używane w~testach interfejsu korzystają z~tych samych schematów. Zmiana kontraktu jest od razu widoczna jako błąd typów po obu stronach.
  \item[Wspólna logika podziału kwot.] Silnik podziału kosztów jest częścią pakietu \texttt{contracts}, z~którego korzystają klient i~serwer, więc formularz wydatku pokazuje dokładnie te kwoty, które zapisze serwer.
  \item[Gospodarstwo jako organizacja Better Auth.] Biblioteka Better Auth dostarcza organizacje z~rolami, członkostwem i~zaproszeniami. Gospodarstwo domowe jest taką organizacją, a~dane aplikacji (ustawienia modułów, historia członkostwa, wydatki, listy) przechowywane są w~osobnych tabelach. Tabele pochodne uzupełniają wyzwalacze bazy danych, więc są aktualne niezależnie od tego, w~jaki sposób dodano członka.
  \item[Salda liczone na żądanie.] Salda i~sugestie rozliczeń są wyliczane przy każdym żądaniu z~zapisanych wydatków i~potwierdzonych spłat. Brak pamięci podręcznej sald eliminuje ryzyko ich rozbieżności z~danymi źródłowymi.
  \item[Szeregowanie operacji finansowych.] Każda transakcja zapisująca dane finansowe blokuje wiersz gospodarstwa w~trybie współdzielonym. Usunięcie gospodarstwa i~wyłączenie modułu wydatków, które wymagają rozliczonych sald, blokują ten wiersz w~trybie wyłącznym. Sprawdzenie sald i~zmiana, którą ono chroni, wykonują się w~jednej transakcji.
  \item[Pliki poza bazą danych.] Załączniki i~awatary trafiają do magazynu obiektów zgodnego z~S3, a~baza przechowuje jedynie ich metadane. Załączniki są prywatne i~udostępniane przez podpisane adresy URL, a~awatary są przechowywane w~osobnym, publicznie dostępnym zasobniku.
  \item[Wymienny dostawca AI.] Funkcje AI korzystają z~jednego wewnętrznego interfejsu, który komunikuje się z~dowolnym API zgodnym z~OpenAI. Dostawcę i~modele wybiera się w~konfiguracji, a~w~testach interfejs zastępuje deterministyczna atrapa.
\end{description}

\subsection{Architektura serwera API}

Serwer API jest podzielony na moduły NestJS odpowiadające obszarom funkcjonalnym: gospodarstwa, użytkownicy, znajomi, kategorie wydatków, wydatki (z~rozliczeniami i~załącznikami), obowiązki, zakupy, pliki i~sztuczna inteligencja. Każdy moduł zawiera kontrolery, które jedynie wiążą trasy z~kontraktami, oraz serwisy z~logiką biznesową i~dostępem do bazy danych.

Każde żądanie do gospodarstwa przechodzi kontrole w~stałej kolejności (tab.~\ref{tab:kontrole-zadan}), więc żądanie z~kilkoma błędami zawsze otrzymuje ten sam kod odpowiedzi. Wszystkie błędy aplikacji mają wspólny format \texttt{\{ code, message, details \}}, nadawany przez globalny filtr wyjątków.

Kroki 1-3 realizują strażnicy (\emph{guards}) NestJS, krok~4 - potoki walidujące (\emph{pipes}) oparte na schematach Zod, a~pozostałe kroki - serwisy. Osobie spoza gospodarstwa serwer odpowiada tak samo jak na zapytanie o~nieistniejące gospodarstwo, aby nie ujawniać istnienia cudzych danych.

\subsection{Architektura aplikacji webowej}

Aplikacja webowa korzysta z~routera App Router frameworka Next.js. Ekrany są pogrupowane według obszarów: strony publiczne, logowanie i~rejestracja, konto, znajomi oraz gospodarstwo, którego podstrony (wydatki, rozliczenia, obowiązki, zakupy, ustawienia) dzielą wspólną powłokę. Powłoka gospodarstwa zna rolę zalogowanego użytkownika, listę członków i~włączone moduły, więc każdy ekran ukrywa niedostępne akcje i~wyłączone moduły.

Dane z~serwera pobierane są przez warstwę API wygenerowaną z~kontraktów i~buforowane przez TanStack Query, który odświeża je po zmianach. Formularze są obsługiwane przez TanStack Form z~walidacją opartą na tych samych schematach co serwer. Interfejs jest zbudowany z~komponentów shadcn/ui i~Tailwind CSS, projektowanych najpierw dla telefonu. Podczas rozwoju i~w~testach aplikacja może działać bez serwera API, ponieważ biblioteka MSW przechwytuje żądania i~odpowiada danymi zgodnymi z~kontraktami.

Przy projektowaniu schematu przyjęto następujące zasady:

\begin{itemize}
  \item kwoty są przechowywane w~kolumnach typu \texttt{bigint} jako liczby całkowite w~jednostkach podrzędnych waluty;
  \item wydatek wraz z~płatnikami, danymi wejściowymi podziału i~wyliczonymi udziałami stanowi jedną całość, zapisywaną i~zastępowaną w~jednej transakcji;
  \item klucze obce do gospodarstwa usuwają dane kaskadowo, natomiast klucze obce do użytkownika blokują usunięcie (\texttt{RESTRICT}), aby nie utracić historii rozliczeń;
  \item historia członkostwa przechowuje każdą parę gospodarstwo-użytkownik, która kiedykolwiek wystąpiła, co pozwala rozliczać byłych członków bez nadawania im dostępu;
  \item spłata nie odwołuje się do wydatku, dlatego edycja lub usunięcie wydatku nie zmienia zarejestrowanych spłat.
\end{itemize}

Do obsługi odczytu paragonów zaprojektowano dodatkowe tabele: \texttt{receipts} (szkic paragonu ze statusem przetwarzania, sprzedawcą, datą, walutą i~sumą), \texttt{receipt\_items} (pozycje z~ilością, ceną jednostkową, rabatem i~kwotą) oraz \texttt{receipt\_item\_assignments} (przypisanie pozycji do osób z~liczbą udziałów). Paragon jest powiązany z~załącznikiem, z~którego go odczytano, i~po zatwierdzeniu z~utworzonym wydatkiem.

\subsection{Zastosowane wzorce projektowe}

\begin{description}
  \item[Moduły i~wstrzykiwanie zależności.] Serwer API składa się z~modułów NestJS, które deklarują swoje zależności, a~kontener wstrzykuje je do kontrolerów i~serwisów. Ułatwia to testowanie i~podmianę implementacji.
  \item[Adapter.] Usługi zewnętrzne (dostawca AI, poczta e-mail i~magazyn plików) są ukryte za wewnętrznymi interfejsami z~wymiennymi sterownikami: produkcyjnym oraz testowym (atrapa AI, zapis wiadomości do dziennika, magazyn w~pamięci).
  \item[Strategia.] Metody podziału kosztów (równy, procentowy, według udziałów, według kwot, z~korektami) są wymiennymi strategiami wyznaczania wag, po których następuje wspólny krok zaokrąglania metodą największych reszt.
  \item[Agregat.] Wydatek z~płatnikami, danymi podziału i~udziałami jest traktowany jako jeden agregat: zmiana finansowa zastępuje go w~całości w~jednej transakcji, nigdy częściowo.
  \item[Obiekt transferu danych.] Dane przesyłane między klientem a~serwerem opisują schematy z~pakietu kontraktów, oddzielone od struktury tabel bazy danych.
  \item[Łańcuch kontroli żądań.] Strażnicy, potoki walidujące i~filtr wyjątków NestJS tworzą łańcuch, w~którym każdy element sprawdza jeden aspekt żądania (tab.~\ref{tab:kontrole-zadan}).
  \item[Idempotentne akcje.] Akcje zmieniające stan, takie jak oznaczenie obowiązku jako wykonanego czy zakupu jako kupionego, można bezpiecznie powtórzyć: ponowne wykonanie nie zmienia wyniku.
\end{description}
