# 4.3.1 Implement household file storage

**Epic:** [4.3 Attachments](4.3.0-epic.md) · **Depends on:** [2.2](../../2-households/2.2-feature-settings.md)

**Goal:** The backend stores uploaded files per household and serves them only to that household's members.

**Scope:** An attachment table with its migration, a storage adapter with an S3-compatible implementation (for example MinIO in development) and an in-memory one for tests, and upload/download endpoints. This task adds the attachment contracts. Linking files to expenses is handled in 4.3.2, and receipts reuse the same storage in [7.3](../../7-ai-receipts/7.3-receipt-scanning.md).

**Acceptance criteria:**

- [ ] An attachment stores the household, a storage key, the MIME type, the size in bytes, the uploader from the session, and a created timestamp. The storage key is generated by the server and never derived from the client file name.
- [ ] Uploads are limited to an allowlist of types (JPEG, PNG, WebP, HEIC, PDF) and a configured maximum size. The type is checked from the file content, not only from the declared header.
- [ ] Downloads go through short-lived signed URLs or a streaming endpoint, and both check household membership. Bucket and credentials come from environment config.
- [ ] Files that nothing references after a configured time (abandoned uploads) can be cleaned up, and the cleanup policy is documented.
- [ ] Tests cover type and size validation, cross-household access, and a failed storage write leaving no attachment row.
