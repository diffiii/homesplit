# 1.1 Decide household identity, permissions, lifecycle, and API conventions

**Epic:** [1 Foundation](1.0-epic.md) · **Depends on:** none

**Goal:** One short decision record that every feature task follows, so policies don't get redesigned during code review.

**Scope:** A document (for example `docs/decisions.md`) covering the household/organization mapping, the role matrix, data lifecycle, and shared route conventions. Reuse Better Auth for authentication and invitations rather than building a parallel system.

**Acceptance criteria:**

- [ ] **Identity:** `householdId` is the organization ID, and the three feature flags are stored in an organization-keyed table.
- [ ] **Permissions:** A matrix lists read, create, update, delete, and action rights per feature and role. It explicitly covers editing and deleting expenses, recording payments on behalf of others, and changing settings.
- [ ] **Lifecycle:** The record defines how departed members appear in history and balances, which household routes they may access, and whether they can record payments themselves or an authorized current member must record on their behalf. It defines supported user and organization deletion without cascading loss of financial history, and what a disabled module allows.
- [ ] **Membership history:** The record chooses where past membership is preserved after Better Auth removes an active `member` row, including retention on user or organization deletion. Task 2.1 implements that storage and lifecycle integration.
- [ ] **Payment parties:** Eligibility uses current membership, preserved membership history, or participation in the household's ledger, without requiring balance aggregation.
- [ ] **Historical expense edits:** The record defines whether departed users already listed as payers or participants remain eligible during financial replacement, separately from eligibility for newly added users. It covers correcting an old expense's total after a participant leaves, so 4.1.4 can validate edits without silently removing historical participants.
- [ ] **API conventions:** The record defines URL shapes for household-scoped routes (`/api/households/:householdId/...`) and user-scoped routes (`/api/me/...`). It defines status codes with the `ApiError` envelope for invalid, unauthenticated, forbidden, not-found, conflict, and empty-patch cases. It defines list ordering and pagination metadata, and how these coexist with Better Auth's own endpoints.
- [ ] **Friend-request privacy:** The record chooses and documents the unknown-email response and its account-discovery implications for 3.2. A successful `FriendRequest` must contain a real `FriendUser` with an ID. If the privacy policy requires a different response shape, propose the contract change before implementing it.
- [ ] **Route doc template:** A short template that each feature task uses to document its routes, schemas, and permissions.
