# 2.1 Enforce household membership and resource isolation

**Epic:** [2 Households](2.0-epic.md) · **Depends on:** [1.2](../1-foundation/1.2-test-infrastructure.md), [1.3](../1-foundation/1.3-contract-validation-errors.md)

**Goal:** A valid resource UUID or an active organization in the session never grants access to a household on its own.

**Scope:** A reusable guard and service helpers for authentication, membership, roles, and household-scoped resource lookups, plus the preserved membership storage and Better Auth lifecycle integration chosen in 1.1.

**Acceptance criteria:**

- [ ] The acting user always comes from the session, and client-supplied author, creator, or completer IDs are ignored or rejected.
- [ ] Membership is checked against the requested `householdId`, not `session.activeOrganizationId`.
- [ ] Past membership is persisted using the 1.1 design before active membership is removed. Existing members are backfilled, and organization creation, joining, leaving/removal, and rejoining through Better Auth keep that history consistent. Historical membership does not confer an active role.
- [ ] Helpers apply the [1.1](../1-foundation/1.1-decisions-household-permissions-api.md) role matrix and reject references to another household's resources or ineligible users.
- [ ] HTTP tests cover nonmembers, removed members under the 1.1 lifecycle rules, forged actor fields, and mismatched household/resource IDs. Lifecycle tests prove that membership history survives removal and rejoining and supports household-scoped eligibility checks.
