# 1.5 Build the API layer

**Epic:** [1 Foundation](1.0-epic.md) · **Depends on:** [1.1](1.1-web-app-scaffold.md), [1.2](1.2-endpoint-map.md)

**Goal:** Screens call typed functions and hooks, and every response and error has one predictable shape.

**Scope:** A fetch client generated from the endpoint map, the Better Auth client with the organization plugin, one error type for both, session handling, and TanStack Query conventions.

**Acceptance criteria:**

- [ ] A call names an endpoint from the map and passes typed params, query, and body. Query values are encoded with the contract codecs, and responses are parsed with the response schema. A response that doesn't match its schema is reported as an error, not passed on.
- [ ] Errors from `/api` routes and from `/api/auth/*` become one error type with the status, `code`, `message`, `details`, and the source. Validation `details.issues` can be mapped onto form fields by path.
- [ ] Only a 401 from an `/api` route, or a session check that finds no session, sends the user to sign-in with a `redirectTo`. Better Auth 401s such as `YOU_ARE_NOT_ALLOWED_TO_DELETE_THIS_MEMBER` are shown as errors instead.
- [ ] The Better Auth client always passes `organizationId` explicitly and never calls `set-active` or other disabled paths.
- [ ] TanStack Query has a query-key factory scoped by household, refetches on window focus, and has helpers for optimistic updates with rollback and for invalidating related queries after a mutation.
- [ ] 429 `RATE_LIMITED` and 500 answers show a toast, and other errors are left to the calling screen.
